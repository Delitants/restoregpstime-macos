# Release procedure

## Self-signed 0.1.0 previews

The user authorized public self-signed previews as two separate GitHub releases. They use tags `v0.1.0-selfsigned-arm64` and `v0.1.0-selfsigned-x86_64`, both pointing to `927cbd0a2f80cae5ae564ed79ea07757fc251c0f`. Each tag matches the embedded source identity of its packaged app. Documentation can advance on the default branch independently.

Each release contains one architecture's ZIP, `SHA256SUMS.txt`, `RELEASE-INFO.json`, the public signing certificate, installation notes and license notices. Private keys, Keychains, private media, local paths and raw host-security receipts are excluded. The release pages state that the builds are self-signed and unnotarized, and label Intel execution as Rosetta testing. They do not claim physical Intel or macOS 13 qualification.

Before publication, verify the exact ZIP hashes, CRCs, source/tag identity and upload inventory. Keep releases as drafts while uploading, download every asset and compare its SHA-256, then publish each as a prerelease. Read back public release status, tags and assets. Never overwrite existing tags or conflicting assets. The existing `publish-release.sh` remains the notarized stable-release workflow described below.

## Future notarized stable releases

Both stable tags must point to one clean, reviewed source commit: `v1.0.0-arm64` and `v1.0.0-x86_64`. Release names are `RestoreGPSTime-1.0.0-AppleSilicon.{zip,dmg}` and `RestoreGPSTime-1.0.0-Intel.{zip,dmg}`. Candidate packaging alone is not acceptance.

1. Run deterministic tests and the candidate-bound QA executable. Obtain native ARM64/Intel acceptance on macOS 13 and the current supported OS, genuine format/large-video and volume evidence, native UI and Finder/Services/droplets, isolated Finder preferences, an Instruments 10,000-item trace with no batch-induced main-thread stall over 250 ms, relocated offline and downloaded/quarantined Gatekeeper checks. Keep private media/raw paths local.
2. Complete the whole-source review and public-content audit. Audit dependencies/licenses and inspect every Mach-O, deployment target, loaded library and bundled path. Update the support matrices only from actual evidence. A missing gate stays missing.
3. Commit tooling and final code before building. `Scripts/package.sh --arch arm64 --version 1.0.0 --source-commit SHA --output outputs/releases/FRESH_ARM64` (and x86_64) builds local ad-hoc candidates. Add `--identity 'Developer ID Application: …' --keychain-profile EXISTING_PROFILE` only with the user's existing authorized Keychain resources. It does not create credentials. Signing receipts are retained; failed output is never overwritten.
4. Review and bind actual acceptance receipts into each candidate's `release-evidence.json`: reviewed/peer SHA, native host identity, architecture-specific app hashes and `dependencyIdentity` hashes, explicit gate results, privacy audit, Developer ID/hardened runtime, accepted notarization and stapling. The packager observes dependency hashes after signing, and the checker recomputes them from the extracted app; bind each host to that exact candidate. Record actual proof; never replace missing with pass from a build result. Recompute `SHA256SUMS.txt` after the final evidence change. This is a release-review step, not an automatic promotion by the packager.
5. Run `Scripts/check-release.sh --directory CANDIDATE --arch ARCH --source-commit SHA --peer-manifest OTHER/release-evidence.json` for both candidates. The checker verifies real archives, hashes, signatures, runtime inventory and the evidence contract. Retain receipts. Both must pass, including mounted/installed and quarantined native checks recorded in acceptance.
6. Only now verify the authenticated GitHub identity and create/verify `Delitants/restoregpstime-macos` using the connector. Push the audited source at SHA. Use `Scripts/publish-release.sh --repository Delitants/restoregpstime-macos --tag TAG --manifest CANDIDATE/release-evidence.json --peer-manifest OTHER/release-evidence.json` only for the qualified candidates. It checks both sets before mutation, refuses conflicting tags/assets, retains a draft until asset download read-back matches, and retains API receipts. It never deletes or clobbers assets. Existing different content is a conflict to resolve explicitly.

Missing native hosts, private QA arrangements, genuine fixtures or signing resources block stable publication. Cross-compilation, ad-hoc signing and Rosetta do not satisfy those gates. There is no automated public upload of private QA material.

The signing workflow follows Apple's [notarization documentation](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) and [custom command workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow). The packaged database attribution follows [GeoNames' data terms](https://www.geonames.org/export/) and the pinned ExifTool Geolocation module's provenance.

A Gatekeeper result with a policy override does not qualify. Acceptance requires the normal notarized Developer ID assessment; do not change global security policy for testing. An existing untagged draft must target the exact source SHA. Moving branch aliases and mismatched targets block publication before uploads; the final tag is read back after publication.

The current native host targets are architecture-specific: Apple Silicon on macOS27 and Intel on macOS26, plus both on macOS13. Apple's [macOS27 compatibility list](https://support.apple.com/en-us/127255) contains Apple Silicon models; its [macOS26 list](https://support.apple.com/en-us/122867) includes supported Intel models. Both candidate manifests must record `currentOSMajorByArchitecture` as `{"arm64":27,"x86_64":26}`. A macOS27 Intel record cannot replace the Intel26 acceptance gate.
